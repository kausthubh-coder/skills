Build a local skills dashboard, fed by an audit that reads your threads every two days

You want to see whether your skills are doing their job: how often each one loads, where it should have loaded and didn't, and how you reacted. Today that takes a manual audit like the one we did on 13 October. This makes it automatic.

  • What you get: a small live site, one click from T3's preview. It shows skill loads, misses, your frustration and praise, repeated instructions, and the audit's suggestions.
  • How it stays current: a T3 scheduled task opens a fresh thread in this repo every 48 hours. That thread reads your new threads, judges them, writes suggestions, and can extend the site itself.
  • Covers Critly too: its two skills and its check runs, the Critly project's threads, and the dashboard itself is built to pass Critly's check.
  • Main risk: word lists misread tone. The audit has a model confirm every signal before it's counted.

The collector counts; it never judges

scripts/collect.mjs reads your Claude Code sessions, your Codex sessions, and T3's thread list (read-only), so each session maps to its thread and project. It records every skill load and how it happened: the agent picked it, you typed /name, or a routing line sent it. It also flags candidate misses and signals in your messages, then writes reports/dashboard/data.json. It only reads what changed since the last run, so opening the dashboard refreshes it.

The audit reads your actual threads, then proposes

A project skill in this repo, audit-skills, runs the collector first, which points it at what changed. Then it reads every thread that had new activity since the last audit with T3's thread tools: your messages in full, the agent's final answers, and the tool calls where a skill should have run. Helper agents read threads in parallel and report back; the main agent makes the calls. It decides which signals are real, catches what a word list can't (a correction phrased politely, a "done" that you disproved two messages later), grades each skill that ran, and turns repeated instructions into rule ideas for /correct. If a description or the routing block changed, it reruns the trigger tests. It writes its report as an HTML page. It never changes a skill without your OK.

The dashboard is a small live site that the audit agent also edits

A small React site served by Bun. It reads the collector's data live, so numbers are current whenever you open it, and a "Recollect" button refreshes them. It also reads what the audit wrote: verdicts, grades and Suggestions (skills to add, retire or fix, AGENTS.md lines, upstream skills worth copying, project fixes). Each audit run may also change the site itself, adding a section when it finds something worth tracking; those edits must pass the typecheck, lint:ui and a taste pass before the run commits them. The feel follows Critly's Product Feel and Density concepts: compact and quiet, one accent color for "needs you", tabular numbers.

You never type a command to see it

A T3 project action, "Dashboard", starts the site and opens it in T3's preview with one click. Each audit thread ends by opening the preview on what changed.

A Bun page beats a Next.js app or a regenerated HTML file

OptionGoodCosts
Bun page pickOne command, on your stack, filters and drill-downs work, reads fresh data on openA small server to start
Next.js appYour default for real web appsA framework, a build and a config for one page you use alone
Static HTML from each auditNothing to run, opens anywhereStale between audits; filtering hundreds of signals gets clumsy

The page is a tool you click around in, not something deployed or shared, so a framework adds weight without buying anything. The audit still writes each report as a standalone HTML page, so you can read any run without starting the dashboard.

In scope: your machine and your history; out: anything cloud

  • In: Claude Code, Codex and T3 history on this machine. All your projects. Library and Critly skills. Trigger test results.
  • Out: deploying the dashboard, sharing data anywhere, editing skills automatically, and history from other machines.
  • Privacy: this repo is public. Data, quotes and audit pages live under reports/, which is gitignored. Only code and the skill get committed.
  • Main checkout: the build and the scheduled audit run on this repo's main checkout, not a worktree. You're switching its threads to local.

Three ways this could fail, and what prevents each

Tone misread

A word list flags "this is stupid" about a bug as anger at the agent. Every signal is confirmed by the audit before it counts, and the feed shows the quote so you can overrule it.

Noise you stop reading

Too many low-value recommendations and you ignore the page. The audit ranks them and shows at most five open ones; the rest wait.

Cost creep

Reading every thread every run would be slow and expensive. The collector is incremental, and the audit only reads threads with activity since its last run.

The site rots as agents edit it

Every run adding a view turns it into a junk drawer. A run may add at most one section, must pass the checks, and should remove a view nobody needed before adding one.
